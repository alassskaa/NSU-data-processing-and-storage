# Сортировка связного списка несколькими нитями

Родительская нить читает строки и добавляет их в начало списка (строки длиннее
80 символов режутся на части), пустая строка выводит текущее состояние списка.
Несколько дочерних нитей бесконечно сортируют список пузырьком с задержками
между шагами и внутри шага. Есть две реализации списка: собственный
односвязный список с блокировкой на каждом узле и
`Collections.synchronizedList(new ArrayList<>())`.

## Структура

| Класс | Назначение |
|---|---|
| `LinkedStringList` | собственный односвязный список: фиктивная голова, `ReentrantLock` в каждом узле, реализует `Iterable<String>` |
| `ArrayStringList` | тот же интерфейс поверх `Collections.synchronizedList(new ArrayList<>())` |
| `SortableList`, `BubblePass` | общий интерфейс списка и одного прохода пузырька |
| `Sorter` | дочерняя нить: бесконечные проходы пузырька, счётчик шагов |
| `SorterPool` | запуск и остановка сортирующих нитей, суммарное число шагов |
| `ListKind` | выбор реализации и теоретическая оценка числа шагов |
| `LineSplitter` | разрезание длинных строк на записи по 80 символов |
| `Main` | родительская нить: ввод строк и вывод списка |
| `StepExperiment` | замер числа шагов для обеих реализаций |

## Запуск

Сборка:

```bash
./gradlew jar
```

Интерактивная программа:

```bash
java -jar build/libs/Java_2-0.0.1-SNAPSHOT.jar linked 4 1000 1000
```

Параметры (все необязательные):

- `linked` или `array` — собственный список или `synchronizedList` (по умолчанию `linked`);
- `4` — количество сортирующих нитей;
- `1000` — задержка между шагами, мс;
- `1000` — задержка внутри шага, мс.

Строки вводятся по одной, пустая строка выводит список, `Ctrl+D` завершает
программу и печатает, сколько шагов сделала каждая нить и какова теоретическая
оценка.

То же через Gradle:

```bash
./gradlew run -q --console=plain --args="array 4 1000 1000"
```

Замер числа шагов:

```bash
./gradlew runExperiment --args="1,2,4,8 100 100 50 10"
```

Аргументы: количества нитей через запятую, задержка между шагами (мс), задержка
внутри шага (мс), число записей, длительность одного прогона (с). Для каждого
количества нитей по очереди запускаются обе реализации на одном и том же
наборе строк.

Тесты:

```bash
./gradlew test
```

## Собственный список

Узел хранит строку (`final`), ссылку `next` и собственный `ReentrantLock`.
Голова списка — фиктивный узел без строки.

- **Вставка в начало** захватывает только голову.
- **Шаг сортировки** захватывает три соседних узла строго от головы к хвосту:
  `before`, затем `first = before.next`, затем `second = first.next`. Потом
  идёт задержка внутри шага, и если `first > second`, переставляются три
  ссылки: `before.next = second`, `first.next = second.next`,
  `second.next = first`. Строки между узлами не переносятся. После этого все три
  блокировки отпускаются, и задержка между шагами проходит без единой
  захваченной блокировки, поэтому вывод в этот момент не ждёт.
- Следующий шаг начинается с того узла, на котором остановились (`second`, если
  была перестановка, иначе `first`). Проход заканчивается, когда за этим узлом
  меньше двух записей, и нить начинает новый проход с головы.
- **Вывод** идёт обычным `for (String s : list)`. Итератор двигается
  «перехватом»: держит блокировку текущего узла, захватывает следующий и только
  после этого отпускает текущий. Пока итератор держит узел `X`, никакая
  перестановка не может затронуть `X` и ссылку `X.next`, ведь для этого нужна
  блокировка `X`. Значит, уже выведенная запись не может оказаться впереди
  итератора, а ещё не выведенная — позади него, и каждая запись выводится ровно
  один раз. Количество и содержимое выведенных записей всегда совпадают с
  введёнными строками, хотя порядок может быть частично отсортированным.
- **Мёртвых блокировок нет.** Любая нить захватывает следующий узел, только
  удерживая его предшественника, то есть всегда в порядке от головы к хвосту.
  Пока узел захвачен, ссылка на его соседа не меняется, поэтому цепочка
  ожиданий идёт строго вперёд по списку и не может замкнуться.
- **Весь список не блокируется.** Одна нить держит не больше трёх соседних
  узлов и только на время одного шага.

## Вариант с synchronizedList

`Collections.synchronizedList` даёт ровно один монитор — сам объект списка.
Отдельные `get`/`set` атомарны, а шаг целиком (прочитать два соседних элемента,
сравнить, записать) — нет. Между вызовами родительская нить может вставить
строку в начало (все индексы сдвинутся), а другая сортирующая нить может
переставить те же элементы, и тогда строка задвоится или пропадёт. Поэтому шаг
выполняется в `synchronized (list)`, и задержка внутри шага оказывается внутри
этого блока. Задержка между шагами — снаружи. Перестановка делается через
`set`: в массиве меняются ссылки, сами строки не копируются. Вывод — for-each
внутри `synchronized (list)`, как требует документация `synchronizedList`.

Другого способа сохранить атомарность шага обёртка не даёт, поэтому на время
одного шага захватывается весь список (но не на всю сортировку).

## Теоретический расчёт

Обозначения: `N` — число сортирующих нитей, `T` — время работы, `d_м` —
задержка между шагами, `d_в` — задержка внутри шага, `L` — число записей.
Время на сравнение и перестановку ссылок (микросекунды) не учитывается.

**Собственный список.** Одна нить делает шаг за `d_в + d_м`. Нить держит только
три соседних узла и только `d_в`, поэтому нити, которые находятся в разных
местах списка, друг другу не мешают и работают параллельно:

```
S_свой = N · T / (d_в + d_м)
```

**synchronizedList.** Задержка внутри шага проходит под единственным монитором,
поэтому в каждый момент шаг выполняет не больше одной нити, и за время `T` все
нити вместе сделают не больше `T / d_в` шагов. Кроме того, каждая нить
не может делать шаги чаще, чем раз в `d_в + d_м`. Итого:

```
S_библ = min(N · T / (d_в + d_м), T / d_в)
```

Монитор насыщается при `N ≥ 1 + d_м / d_в`. Дальше число шагов не растёт:
лишние нити только дольше ждут монитор.

Пример для задержек по 1 с, `N = 4`, `T = 60 с`:
`S_свой = 4 · 60 / 2 = 120`, `S_библ = min(120, 60) = 60`.
В общем случае `S_свой / S_библ = max(1, N · d_в / (d_в + d_м))`.

## Результаты измерений

Замеры сделаны программой `StepExperiment` на списке из 50 случайных строк.
Во всех прогонах после остановки нитей в списке остались ровно те же
записи, что были вставлены.

**1. `d_м = d_в = 100 мс`, `T = 10 с`**

|---|---:|---:|---:|---:|
| 1 | 50 | 48 | 50 | 48 |
| 2 | 100 | 96 | 100 | 96 |
| 4 | 200 | 179 | 100 | 96 |
| 8 | 400 | 327 | 100 | 96 |

**2. `d_м = 300 мс`, `d_в = 100 мс`, `T = 10 с`** (монитор насыщается при `N = 4`)

| N | свой: теория | свой: факт | synchronizedList: теория | synchronizedList: факт |
|---|---:|---:|---:|---:|
| 1 | 25 | 25 | 25 | 25 |
| 2 | 50 | 49 | 50 | 49 |
| 4 | 100 | 96 | 100 | 96 |

**3. `d_м = d_в = 100 мс`, `T = 60 с`**

| N | свой: теория | свой: факт | synchronizedList: теория | synchronizedList: факт |
|---|---:|---:|---:|---:|
| 4 | 1200 | 1136 | 600 | 578 |
| 8 | 2400 | 2225 | 600 | 578 |

**4. `d_м = d_в = 1 с`, `N = 4`, `T = 60 с`**

| | теория | факт | шагов по нитям |
|---|---:|---:|---|
| свой список | 120 | 107 | 29, 28, 25, 25 |

## Объяснение

**synchronizedList совпадает с теорией почти точно (0,96–0,98).** Как только
нитей становится достаточно для насыщения монитора, суммарное число шагов
перестаёт зависеть от `N`: 96 шагов за 10 секунд и при 2, и при 4, и при 8
нитях. Во втором опыте рост линейный до `N = 4` (25 → 49 → 96), после чего
останавливается. Шаг вместе с задержкой внутри шага выполняется под
единственным монитором, поэтому нити фактически работают по одной. Добавленные
нити только делят те же `T / d_в` шагов между собой. Монитор `synchronized`
не гарантирует очерёдности, поэтому делятся шаги неравномерно (7, 14, 23, 15).

**Собственный список масштабируется с числом нитей:** за 10 секунд при 8 нитях
выходит 327 шагов против 96, за 60 секунд — 2225 против 578. Каждый шаг
блокирует только три соседних узла, поэтому шаги разных нитей и их задержки
идут одновременно.

Отставание от теории складывается из двух причин.

1. `Thread.sleep` никогда не просыпается раньше срока и обычно опаздывает
   на несколько миллисекунд. При задержках по 100 мс это даёт около 4% шагов:
   столько же теряет одна нить и вариант с synchronizedList. При задержках по
   1 с потеря меньше 2%.
2. Нити сталкиваются в начале работы. Все они начинают проход с головы и
   сначала стоят в очереди за одними и теми же узлами. Две нити могут идти
   друг за другом без помех: одна держит свои три узла, пока другая спит между
   шагами. Окно третьей нити уже пересекается с окнами соседей, поэтому
   последние нити ждут и отстают (по нитям 48, 47, 44, …, 34). Когда нити
   разошлись по списку, они движутся с одинаковой скоростью и больше
   не встречаются: дойдя до конца, каждая возвращается в голову в своё время,
   и расстояние между нитями сохраняется. Если сравнить 10- и 60-секундные
   прогоны с 8 нитями, первая нить за дополнительные 50 секунд сделала
   288 − 48 = 240 шагов, последняя — 270 − 34 = 236. Это почти идеальные
   250 минус те же 4% на `sleep`. Поэтому с ростом `T` доля потерь падает:
   0,817 за 10 секунд и 0,927 за 60 секунд при 8 нитях. В опыте 4 за 60 секунд
   помещается всего 30 шагов одной нити, меньше одного прохода по 50 записям,
   то есть весь замер приходится на начальную фазу (0,89).

Итог: собственный список с блокировкой на узел позволяет нитям сортировать
параллельно, и число шагов растёт примерно пропорционально числу нитей.
`synchronizedList` даёт один замок на весь список, поэтому шаги идут строго
по одному, и скорость сортировки ограничена величиной `1 / d_в` при любом
числе нитей. Это заметно и пользователю: в варианте с synchronizedList вывод
и вставка тоже ждут монитор, который при насыщении почти всегда занят. В
собственном списке вывод ждёт только тогда, когда проходит через узлы,
захваченные шагом в эту самую секунду.
